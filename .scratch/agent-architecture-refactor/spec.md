# Agent 框架分层重构

**Status:** ready-for-agent

## Problem Statement

当前仓库是学习 LLM Agent 的入口，目标是覆盖一个标准 Agent 的完整模块，并允许复杂模块先预留接口。现状是：主链路（messages / llm / tools / agent）可跑，但"循环"和"agent 定义"混在一个类里；工具层反向依赖 LLM 层；通用桌面能力与应用专属的扫雷逻辑混在框架包内并产生循环导入；system prompt 每轮重复写入历史，工具轮的 assistant 文本被丢弃；没有流式输出、统一事件流、上下文装配层和依赖方向守护；多数复杂模块只有孤立接口，没有接入真实链路。结果是学习者无法看清一个标准 Agent 的完整模块边界与协作方式，维护者也难以在调整架构时不引入新的耦合。

## Solution

按已确认的分层架构重构为：`core`（消息/事件/错误/配置）、`llm`、`tools`、`memory`、`obs`、`context`、`runtime`、`capabilities`（retrieval / multi_agent / guardrails / hitl / mcp / sandbox / computer_use）、`eval`、`interfaces`，以及框架之外的 `apps/minesweeper`。以 `AgentRuntime` 为唯一循环引擎，`AgentSpec` 为无状态定义，`Session` 持有状态，统一事件流承载流式、追踪、审批与评测。复杂能力做到"最小闭环"或"接口 + 空实现真实接线"，保证流程完备。全程按 P0–P5 分阶段推进，每阶段可运行、测试全绿；扫雷在 P0–P3 允许离线，P4 恢复并与新运行时接通。

## User Stories

1. 作为学习者，我想按 `core → llm/tools → runtime → context → capabilities` 的顺序阅读代码，以便逐层建立心智模型。
2. 作为学习者，我想每个模块有单一职责与清晰协议，以便不读完整仓库也能理解一个模块。
3. 作为学习者，我想看到一次运行的完整事件序列，以便理解 Agent 循环每一步发生了什么。
4. 作为学习者，我想用 fake LLM 运行示例与测试，以便没有 API key 也能学习全部机制。
5. 作为学习者，我想看到流式输出的增量事件，以便理解流式输出与工具调用如何共存。
6. 作为学习者，我想看到 system prompt、历史、记忆召回、检索片段如何装配成一次请求，以便理解上下文工程。
7. 作为学习者，我想看到记忆压缩前后的差异，以便理解长会话的 token 管理。
8. 作为学习者，我想每个"仅接口"的模块在真实链路上都有接线点，以便知道它为什么存在、将来插在哪里。
9. 作为学习者，我想通过 ADR 看到每个关键取舍的理由，以便理解"为什么这样分层"。
10. 作为学习者，我想通过一条本地检查命令发现分层违规，以便理解依赖方向的重要性。
11. 作为学习者，我想示例 01–04 与最终目录结构一致，以便从示例反查到对应模块。
12. 作为学习者，我想每条主链路都能在测试中看到断言，以便把阅读和验证结合起来。

13. 作为框架使用者，我想用 `AgentSpec` 声明式定义 agent（提示词、工具、记忆、策略），以便不写循环代码。
14. 作为框架使用者，我想复用同一个 runtime 运行不同 spec，以便避免行为分叉。
15. 作为框架使用者，我想在 spec 中挂载中间件，以便在不修改循环的情况下加入日志、重试、计划等行为。
16. 作为框架使用者，我想注册自定义工具并自动获得参数 schema 校验，以便减少无效调用。
17. 作为框架使用者，我想同一批工具并行执行，以便降低延迟。
18. 作为框架使用者，我想为工具设置超时与错误分类，以便可恢复错误回填给模型、致命错误终止运行。
19. 作为框架使用者，我想在工具执行前接入审批策略，以便实现 human-in-the-loop。
20. 作为框架使用者，我想在输入与输出接入护栏，以便拦截不合规内容。
21. 作为框架使用者，我想通过 session 进行多轮对话，以便历史与状态被正确保存。
22. 作为框架使用者，我想在任意时刻取消运行并收到明确的结束事件，以便控制长任务。
23. 作为框架使用者，我想设置最大步数，以便防止无限循环。
24. 作为框架使用者，我想替换 LLM provider 或模型，以便适配不同后端。
25. 作为框架使用者，我想接入上下文提供者（记忆、检索、画像），以便按需扩展请求上下文。
26. 作为框架使用者，我想让失败的会话恢复时保留完整历史（包含工具失败），以便模型能基于真实状态继续。
27. 作为框架使用者，我想通过统一配置设置模型、超时、预算与日志，以便不在代码里散落硬编码。
28. 作为框架使用者，我想在运行结束时拿到结构化结果（最终文本、用量、步骤数），以便程序化处理。
29. 作为框架使用者，我想复用同一套工具定义在运行时与测试中，以便测试与生产行为一致。

30. 作为维护者，我想依赖方向被自动检查，以便重构后不会重新出现循环导入和反向依赖。
31. 作为维护者，我想工具层不依赖 LLM 层，以便工具可独立使用和测试。
32. 作为维护者，我想 `core` 不依赖任何内部模块，以便协议与类型保持稳定。
33. 作为维护者，我想能力层不依赖接口层，以便服务端变化不影响能力实现。
34. 作为维护者，我想框架包不依赖 `apps` / `examples`，以便框架可被复用。
35. 作为维护者，我想在本地一条命令运行 lint、类型检查、依赖检查与测试，以便 Windows 与 macOS 行为一致。
36. 作为维护者，我想每个重构阶段结束时代码可运行、测试全绿，以便随时暂停和恢复。
37. 作为维护者，我想旧路径被彻底删除而不是保留兼容层，以便代码库没有双轨制。
38. 作为维护者，我想装配结果不写入持久历史，以便 system prompt 不再重复累积。
39. 作为维护者，我想工具轮的 assistant 文本被完整保存，以便多步推理的上下文不丢失。
40. 作为维护者，我想工具失败也进入历史，以便下一轮模型能看到真实执行结果。

41. 作为扫雷应用开发者，我想通用截屏、鼠标、观察、标注能力留在框架，以便复用到其他桌面任务。
42. 作为扫雷应用开发者，我想棋盘几何、扫雷工具、提示词与启动逻辑放在 `apps`，以便应用独立演进。
43. 作为扫雷应用开发者，我想重构后仍能自动对局，以便验证框架在真实场景中可用。
44. 作为扫雷应用开发者，我想在无真实 API 的情况下用 fake LLM 跑完整 e2e，以便本地快速回归。
45. 作为扫雷应用开发者，我想迁移期间不被迫维护两套入口，以便重构负担可控。

46. 作为评测者，我想用精确匹配与正则评测器对 fake 或真实 LLM 跑批，以便看到结构化报告。
47. 作为评测者，我想 trace 记录每步耗时、工具调用与 token 用量，以便分析失败原因。
48. 作为评测者，我想复用 runtime 的事件流做评测，以便不重复实现调用逻辑。

49. 作为 HTTP 服务调用者，我想通过一个端点发起对话并收到流式事件，以便构建前端。
50. 作为 HTTP 服务调用者，我想服务端支持多会话隔离，以便不同会话互不干扰。

51. 作为检索使用者，我想用最小 RAG 流水线把外部文档注入上下文，以便验证检索与上下文装配的协作。
52. 作为检索使用者，我想用确定性假 embedder 跑测试，以便结果可复现且不依赖外部服务。
53. 作为多 Agent 使用者，我想用顺序编排把任务拆给多个 agent，以便理解协作模型。
54. 作为多 Agent 使用者，我想在接口上看到并行与交接的扩展点，以便未来扩展而不改核心。
55. 作为框架使用者，我想在工具审批、护栏、沙箱未实现时仍能正常运行，以便逐步补齐能力。

## Implementation Decisions

- **分层与依赖方向**：`core` 为最底层且不依赖内部模块；`llm`、`tools`、`memory`、`obs` 只依赖 `core`；`context` 依赖 `core` 与 `memory`；`runtime` 依赖 `core`、`llm`、`tools`、`memory`、`obs`、`context`；`capabilities` 可实现 `runtime` / `context` 定义的协议；`interfaces` 负责组装。禁止 `tools → llm`、`capabilities → interfaces`、框架 → `apps/examples`。用 import-linter 守护。
- **运行时与定义分离**：`AgentSpec` 无状态，包含提示词、模型配置、工具、上下文提供者、记忆、步数上限、中间件、护栏、审批策略与元数据；`AgentRuntime` 是唯一循环引擎；对外入口为 `run(spec, session, input)`，返回事件流，另有收集为结构化结果的便利方法。
- **会话与状态**：`Session` 持有全部可变状态（记忆、运行状态、审批记录等），具体实现在接口层，运行时只依赖 `Session` 协议。
- **统一事件流**：运行产出 `RunStart`、`StepStart`、`ContextBuilt`、`LLMDelta`、`LLMCompleted`、`ToolCallRequested`、`ToolResult`、`RunEnd`、`Error` 事件；Tracer、UI、评测与审批均为事件消费者。
- **流式**：LLM 供应商协议同时提供整包与流式调用；OpenAI 兼容实现首版支持流式、用量提取与可配置重试。
- **上下文与记忆分离**：上下文装配负责每轮请求视图（system、压缩历史、记忆召回、检索片段），装配结果不写回持久历史；记忆负责存取与压缩。首版实现会话历史与摘要滑窗压缩；长期记忆（画像/语义/情景）仅协议。
- **工具系统**：工具定义自包含，不依赖 LLM 类型；执行前做 JSON Schema 校验；同批工具并行执行；支持超时与错误分类；可恢复错误作为工具结果回填，致命错误终止运行；沙箱与动态工具提供者首版仅协议并真实接线。
- **扩展协议**：中间件、护栏、审批策略由运行时定义；上下文提供者由 context 定义；检索、多 Agent、沙箱、MCP、计算机使用在能力层实现或预留给协议。
- **能力深度**：完整实现 core、llm、tools、runtime、context、session、computer_use、minesweeper 应用；最小闭环实现 obs、retrieval、eval、multi_agent（顺序编排）、cli、server、摘要压缩；接口 + 空实现实现 guardrails、mcp、sandbox，hitl 提供自动批准与控制台审批。
- **框架与应用边界**：通用计算机使用能力留在框架；扫雷棋盘几何、工具、提示词与启动逻辑移入应用目录；目标游戏程序不变；框架禁止引用应用。
- **配置**：统一配置来源，禁止裸字典；模型、超时、步数、token 预算、日志目录均可配置；应用通过显式参数传入配置。
- **工程工具**：本地引入 lint/format、类型检查（核心四包严格）与依赖检查，统一由一条本地脚本执行；暂不启用云端 CI。
- **迁移策略**：允许破坏性重构，不保留兼容层；每个阶段结束测试全绿；扫雷在 P0–P3 允许离线，P4 一次性迁移并恢复；真实 API 人工验收安排在基本完备版本达成之后。

## Testing Decisions

**好测试的标准**：只通过公共接口验证外部行为，不 mock 内部协作者、不测私有函数；期望值来自独立事实来源（规格、已知常量、手工推演的样例），不按实现方式重算；每个测试读起来像一条能力说明，重构后仍应通过。

**已确认的接缝**：

- **S1 主接缝**：`AgentRuntime.run(spec, session, input)`。用脚本化 fake LLM（记录收到的 messages、返回工具调用、可分片流式）、fake 工具与 fake 上下文提供者驱动；断言事件序列、结构化结果、session 历史与 provider 收到的请求。覆盖循环、上下文装配、工具执行与错误回填、步数限制、取消、中间件、护栏与审批接线、记忆压缩。
- **S2 供应商协议接缝**：LLM 供应商的整包与流式调用。用伪 wire chunk 验证消息转换、流式组装、用量提取与错误映射，不访问真实网络。
- **S3 外部边界接缝**：
  - 计算机使用：以屏幕后端与鼠标后端协议为边界，测试使用 fake backend；扫雷 e2e 走 S1 + fake LLM + fake backend。
  - 服务端：以 `AgentService` / `SessionManager` 为接缝；可选一个 HTTP/SSE 冒烟测试。
  - 检索：以 embedder / retriever 协议为接缝，确定性假 embedder 保证可复现。
  - 多 Agent 与评测：以 orchestrator / evaluator 公共接口为接缝。

**测试范围**：核心四包重点覆盖外部行为；能力层每个模块至少一个最小闭环测试；接口层测会话隔离与流式输出；应用层测扫雷工具与 e2e。不测试私有函数与内部协作者。

**既有先例**：现有测试已用 fake LLM 驱动 agent 循环、覆盖多模态消息的线上协议转换，并以 fake 方式测试桌面边界，可沿用同样的模式。

**验收**：每阶段 `pytest` 全绿；本地检查脚本（lint、format、类型、依赖、测试）通过；扫雷 e2e 在 P4 通过；真实 API 人工验收在基本完备版本之后进行。

## Out of Scope

- 生产级多租户、鉴权、分布式执行与高可用。
- 完整 MCP、沙箱、向量数据库实现；仅提供接口与空实现。
- OpenAI 兼容之外的供应商矩阵。
- 前端 UI；服务端只提供最小 HTTP/SSE 能力。
- 云端 CI（GitHub Actions）暂不启用。
- 旧 API 兼容层与双轨目录。
- 重写 `games/minesweeper.py` 目标程序。
- 自动化测试中调用真实 LLM API。
- 长期记忆（画像/语义/情景）的完整实现。
- 并行多 Agent 与 agent 交接的完整实现。
